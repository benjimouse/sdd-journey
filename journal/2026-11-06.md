# Theatre Lines — SDD Learning Journal

## Why I'm doing this

I'm building Theatre Lines, an application to help amateur actors learn their lines, as a practical way of exploring Spec-Driven Development (SDD) and AI-assisted software engineering.

I'm approaching this primarily as an Engineering Manager, rather than as a developer trying to learn a new framework.

My priorities are:

1. Understand how SDD works in practice.
2. Understand how SDD changes the responsibilities of an Engineering Manager.
3. Learn to work effectively with AI coding agents.
4. Understand the tools and ecosystem.
5. Build a useful application along the way.

I want the AI to do much of the implementation, but I want to understand and retain ownership of the important decisions.

## Session 1 — 7 November 2026

**Duration:** Approximately 2 hours  
**Focus:** Development environment, AI agent setup and project constitution

### What I did

- Checked and prepared my Mac development environment.
- Installed and configured GitHub Spec Kit.
- Started with Gemini CLI, but encountered Google Workspace licensing and API billing issues.
- Switched to Antigravity CLI using a personal Google account.
- Configured Spec Kit to use Antigravity.
- Generated the first version of the Theatre Lines project constitution.
- Reviewed the constitution and identified changes before accepting it.

### What I learned

**1. AI development tooling has operational overhead.**

Getting an agent working isn't necessarily straightforward. Authentication methods, Workspace licensing, API billing and spending controls all matter.

I spent longer than expected on setup. In a team environment, these are issues worth resolving centrally rather than expecting every engineer to work through them independently.

**2. SDD begins before any application code is written.**

The constitution establishes principles and constraints that guide subsequent specifications, plans and implementations.

This should help keep decisions consistent as the project grows and as different AI agents become involved.

**3. AI-generated decisions need reviewing, not just AI-generated code.**

Antigravity produced a plausible constitution, but made some decisions that went beyond what I'd asked for:

- Mandating `user_id` on every database model and API contract.
- Imposing a strict $0 cloud budget when I was happy with controlled spending.
- Introducing specific implementation approaches into the constitution.

These weren't necessarily unreasonable suggestions, but they weren't decisions I'd explicitly made.

**4. Different decisions belong at different stages.**

- **Constitution:** Principles and non-negotiable constraints.
- **Specification:** What the application must do and why.
- **Plan:** How we'll implement it.
- **Tasks:** The work required to deliver it.

Putting implementation decisions into the constitution too early risks restricting future choices without good reason.

### Engineering Manager reflections

The most interesting part so far has been reviewing the constitution.

I didn't need to write it myself, but I did need to recognise where the AI had overstepped, challenge assumptions, and decide what should be changed.

This feels similar to reviewing an architectural proposal from an engineer, rather than reviewing their code.

A question I want to explore further:

**How do I establish enough confidence in AI-generated specifications and plans to delegate implementation without needing to inspect every line of code?**

### Decisions made

| Decision | Reason |
|---|---|
| Use GitHub Spec Kit | Provides a structured, repeatable SDD workflow |
| Use Antigravity CLI initially | Avoids the authentication and billing difficulties encountered with Gemini CLI |
| Use TypeScript, React, Node.js and PostgreSQL | Familiar enough ecosystem, with TypeScript providing a learning opportunity |
| Local-first development | Keeps infrastructure simple and costs controlled |
| Design for future multi-user support | Avoids difficult architectural retrofitting |
| Human approval of significant decisions | Keeps accountability with the engineer rather than the agent |

### What didn't go to plan

- Shell configuration changes temporarily broke iTerm startup. The actual cause was an unrelated change I'd made to my aliases configuration.
- Gemini CLI authentication took substantial time and was ultimately abandoned in favour of Antigravity.
- I initially expected to reach application development much sooner.

**Lesson:** Time-box tooling problems. Switching approach can be more productive than continuing to debug a tool that isn't central to the learning objective.

### Next session

- Commit the constitution to Git.
- Use `/speckit-specify` to define the first feature.

### Open questions

- How much architectural detail belongs in a constitution?
- How should multi-user readiness be designed without implementing authentication immediately?
- What evidence should an Engineering Manager expect before approving AI-generated implementation plans?
- How should we measure whether SDD is actually improving development quality and efficiency?
