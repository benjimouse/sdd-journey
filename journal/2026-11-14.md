# SDD Learning Journal — Week Ending 14 November 2026

## Focus this week

Moving Theatre Lines from initial project scaffolding towards working functionality, while exploring how to supervise an AI coding agent effectively as an Engineering Manager.

## What we achieved

- Completed the backend foundation, including server startup, authentication isolation and real HTTP binding tests.
- Resolved known production dependency vulnerabilities by upgrading Drizzle ORM and Zod.
- Began the first functional feature: extracting ordered text from PDF theatre scripts.
- Implemented and tested PDF extraction (T016/T021), reaching 32 passing automated tests.
- Started building a local CLI to test real scripts, but Antigravity hit its usage quota before final verification.

## Key lessons

### 1. Tests passing does not always mean the behaviour is verified

The backend initially had passing tests, but we realised that they didn't demonstrate that the actual development and compiled processes could start correctly.

We asked Antigravity to launch both processes, check the listening interface, make real HTTP requests and verify clean shutdown.

**Learning:** I need to ask what evidence demonstrates the intended behaviour, not just whether tests are green.

**Future practice:** Include process-level or end-to-end verification where unit tests cannot prove the behaviour.

### 2. Test-first development needs meaningful failures

For PDF extraction, Antigravity wrote tests before implementation and demonstrated that they failed. However, the initial failure was because the implementation module did not yet exist.

This demonstrates sequencing, but doesn't by itself establish that the tests detect incorrect extraction behaviour.

**Learning:** The red-green-refactor cycle is more useful when the red phase demonstrates a meaningful behavioural expectation.

**Future practice:** Review test assertions and representative failure cases, rather than accepting test-first claims at face value.

### 3. Small tasks make AI-assisted development manageable

We resisted asking Antigravity to implement the entire PDF import feature. Instead, we selected T016/T021: tests and implementation for PDF text extraction.

This gave us a coherent piece of functionality that could be reviewed independently.

When the agent subsequently hit its quota during the CLI task, only one untracked directory was left behind.

**Learning:** Small, bounded tasks reduce the cost of interruptions and make verification easier.

**Future practice:** Give the agent a clear scope, explicit exclusions, verification requirements and a stop-for-review instruction.

### 4. Real examples matter more than synthetic success

The PDF extractor correctly processed our *Importance of Being Earnest* fixture, preserving dialogue, speaker labels and stage directions.

However, actual theatre scripts vary substantially in formatting, including differences between directors and editions.

The extractor currently relies on assumptions such as a 3-point vertical clustering tolerance and predominantly single-column layouts.

**Learning:** Passing a carefully constructed fixture is necessary but insufficient to establish real-world usefulness.

**Future practice:** Build a private regression collection from real scripts and short rehearsal extracts. Use observed failures to refine the tests and specification.

### 5. Security decisions should be conscious and proportionate

We addressed production dependency vulnerabilities, achieving a clean production-only npm audit. Development-tool vulnerabilities remain, including serious findings.

Rather than indefinitely delaying functional work, we chose to record the risk and continue development of this local learning project.

**Learning:** Engineering judgement involves understanding risk, context and opportunity cost, not simply maximising one quality metric.

**Future practice:** Revisit outstanding vulnerabilities before exposing the application beyond the local development environment or deploying it to the cloud.

### 6. Agent limits affect engineering workflow

Antigravity exhausted its usage quota while creating the PDF diagnostic CLI. The file exists locally, but its final verification and handover are incomplete.

**Learning:** Agent availability and context limits are practical delivery constraints. A task needs enough capacity for implementation, verification and reporting.

**Future practice:** Keep tasks small and leave the repository at an understandable checkpoint after each iteration.

## What this means for my Engineering Manager role

The most valuable part of my involvement has not been writing code. It has been:

- Choosing the next useful increment.
- Challenging whether verification evidence is sufficient.
- Recognising assumptions and risks.
- Deciding when technical debt is acceptable.
- Keeping scope under control.
- Ensuring another session can resume without rediscovering everything.

This suggests that SDD may shift some of an Engineering Manager's attention from coordinating implementation towards supervising specifications, decisions, evidence and outcomes.

That is an emerging hypothesis rather than a settled conclusion.
